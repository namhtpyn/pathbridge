# pathbridge

A configurable path-to-URL forwarding proxy with a built-in admin UI.

Route selected URL paths to external upstreams through one host — useful when an
upstream API must be reached from a specific network or region, or when you want
a stable public hostname in front of changing backends.

## How it works

- Each **pair** maps a path prefix to a target origin, e.g. `/hook` → `https://api.upstream.example`
- Requests to that prefix are proxied to the target with the upstream's Host header
- Pairs are managed at runtime — add, edit, or remove them from the admin UI, no rebuild
- Longest-prefix match wins; pairs can be individually disabled
- Targets may be a bare origin (`https://api.example.com`) or an origin with path
  (`https://api.example.com/base`) — the path is appended to the forwarded request
- Optional per-pair method allowlist (e.g. `GET, HEAD` for webhook receivers)

## Run

```bash
docker run -d \
  -e DATA_DIR=/data \
  -v pb-data:/data \
  -p 3000:3000 \
  ghcr.io/namhtpyn/pathbridge
```

Put your own TLS terminator (nginx, Traefik, Caddy…) in front; the app itself is plain HTTP.

A default admin account is seeded on first boot (fresh database only — never on
restarts of an instance that already has users):

| env | default |
|---|---|
| `ADMIN_EMAIL` | `admin@pathbridge.local` |
| `ADMIN_PASSWORD` | `pathbridge-admin` |

Change the password after first login, or set the envs before first boot.

## The admin app (`/admin`)

Single-page admin (Nuxt UI, SSR-hydrated) with five tabs:

- **Pairs** — forwarding rules (create/edit/delete via modals, live in the table)
- **Users** — accounts, roles, reset password, email-verified toggle
- **Roles** — RBAC roles with a resource × action permission matrix
  (`action:scope` grammar, e.g. `pairs:read:all`); `admin` and `viewer` are
  builtin and canonicalized at boot, custom roles are fully editable
- **Logs** — access log per pair with status/duration/client
- **Settings** — log retention, password-login toggle, and OIDC providers

The version in the topbar/login screen comes from the image build (`/api/version`).

## Authentication

- **Email + password** (better-auth) — first-boot admin, admin-created users, or
  admin-triggered resets. Public sign-up closes after the first user exists.
- **Multiple OIDC providers** — configure as many as you like in Settings →
  Authentication. Each provider gets an autogenerated id; its redirect URI is
  `<your-base-url>/auth/callback/<provider-id>` (shown next to each provider in
  Settings). Same-email accounts auto-link: an OIDC login whose email matches an
  existing verified local account signs into that account instead of creating a
  duplicate.
- **API keys** — long-lived revocable keys (better-auth api-key plugin) for
  programmatic access; keys inherit their owner's role permissions.
- **Bearer sessions** — session tokens also work as `Authorization: Bearer`
  headers for agents/MCP-style clients.

Disabling password login requires at least one fully-configured OIDC provider
(can't lock yourself out).

## RBAC

Permissions are `resource:action[:scope]` statements attached to roles:
`read | create | update | delete` × `pairs | users | roles | settings | logs`,
scope `own | all` where it applies (`all` implies `own`). Builtin roles:

- `admin` — everything, all scopes
- `viewer` — read own pairs only

Custom roles bundle any set of statements; users get one role (default `viewer`).

## Admin API

Same API the UI uses; session cookie, `Authorization: Bearer <session-token>`
or `Bearer <api key>`:

```
GET    /api/pairs            # list
PUT    /api/pairs            # upsert  {"path":"/hook","target":"https://api.example.com"}
DELETE /api/pairs/hook       # remove by path
GET    /api/users            # list users (users:read)
POST   /api/users            # create {email,name,password,role?,emailVerified?}
PUT    /api/users/:id        # update {name?,email?,role?,emailVerified?}
GET    /api/roles            # roles + statements
PUT    /api/roles/:id        # update role statements/description
GET    /api/settings         # retention + password toggle
PUT    /api/settings         # update the above
GET    /api/oidc             # OIDC providers (secrets masked)
PUT    /api/oidc             # replace provider list
GET    /api/logs             # access log
GET    /api/auth-config      # public: login buttons for the login screen
GET    /api/version          # build version
GET    /health               # liveness
```

better-auth endpoints live under `/auth/*` (sign-in, sign-out, session, api keys).

### Pair fields

| field | meaning |
|---|---|
| `path` | URL prefix to claim (must start with `/`, not `/_`) |
| `target` | upstream origin, optionally with a base path |
| `upstreamHost` | optional Host header override; defaults to target hostname |
| `stripPrefix` | remove the pair's prefix before forwarding |
| `methods` | optional allowlist, e.g. `["GET","HEAD"]` |
| `note` | free-form label |
| `enabled` | `false` to park a pair |

## Configuration

| env | default | purpose |
|---|---|---|
| `DATA_DIR` | `./data` | where `pathbridge.db` lives |
| `PORT` | `3000` | listen port |
| `DRIZZLE_DIR` | `./drizzle` | migrations dir (bundled) |
| `BETTER_AUTH_SECRET` | — | auth secret (set in production) |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | see above | first-boot admin seed |
| `APP_VERSION` | `dev` | baked into the image by CI |

Runtime settings (OIDC providers, retention, password toggle) live in the
database and are edited in the admin UI — no restart needed.

## Tech

- Nuxt 4 (Nitro) — SSR admin, catch-all bridge middleware
- better-auth (drizzle adapter) — email+password, multi-provider OIDC, API keys, bearer
- drizzle-orm rc + bun:sqlite — storage, runtime migrations
- Nuxt UI v4 + Tailwind — admin interface
- 100% strict TypeScript, zod validation on every endpoint (strict backend / loose frontend)

## Notes

- Prefixes starting with `/_` are reserved (admin UI, auth, health, API) and cannot be claimed by pairs.
- State lives in a single SQLite file — mount it on a volume to persist across restarts.
- OIDC provider ids are UUIDs; callback paths are stable for the life of the provider.
